# Флоу возврата билета, оплаченного сертификатом (MVP)

Логическая схема для возврата заказа или части заказа, где в оплате участвовал подарочный сертификат. Только MVP: один сертификат на заказ, смешанный возврат «сертификат + карта», без самостоятельной формы возврата самого сертификата.

## Принятые допущения MVP (пока открытые вопросы не закрыты)

Сумма к возврату считается по правилам события, способ оплаты её не меняет. Сервисный сбор при добровольном возврате участником не возвращается. При отмене события организатором / технической ошибке Timepad сервисный сбор возвращается (ручная или автоматическая ветка по типу инициатора). Восстановление на сертификат идёт в обратном порядке списания: сначала билеты, затем сбор; при возврате сначала закрываем долю сертификата, затем карту. Если исходный сертификат нельзя восстановить, выпускается новый на сумму восстановления. Возврат денег за неиспользованный остаток самого сертификата в этот флоу не входит.

## Детализация ключевых развилок

### 1. Вход в флоу

```
Участник нажал «Вернуть билет»
        ↓
Открыт заказ из ЛК / письма / поддержки
        ↓
Билет ещё действителен?
 ↙             ↘
Нет             Да
 ↓               ↓
Показать статус  Правила события:
уже возвращён /  дедлайн, % возврата,
использован      тип возврата
```

### 2. Расчёт суммы (без изменения правил события)

```
База возврата по правилам события
    ↓
Минус уже возвращённые суммы по этим билетам
    ↓
Нужен ли возврат сервисного сбора?
 ↙                    ↘
Нет (добровольно)      Да (отмена / ошибка / ручной флаг)
 ↓                      ↓
Сумма = билеты         Сумма = билеты + сбор
(или доля по правилам) (или доля по правилам)
```

### 3. Распределение по источникам (MVP)

Порядок списания при покупке: сначала билеты, потом сервисный сбор; внутри суммы сначала сертификат, потом карта.

Порядок возврата: сначала на сертификат (в пределах того, что сертификат реально оплатил в возвращаемых позициях), остаток на карту.

```
Пример A (как в ТЗ)
Билеты 4000 + сбор 400
Сертификат 3000 + карта 1400
Добровольный возврат всех билетов, сбор не возвращаем
    ↓
К возврату: 4000
    ↓
На сертификат: 3000
На карту: 1000
Сбор 400 остаётся у Timepad

Пример B (сертификат покрыл всё)
Билеты 2000 + сбор 200
Сертификат 3000 → списано 2200, остаток 800
Добровольный возврат
    ↓
К возврату: 2000
    ↓
На сертификат: 2000
На карту: 0
Новый баланс: 800 + 2000 = 2800
(200 сбора не восстанавливаем)

Пример C (возврат с восстановлением сбора)
Та же оплата, отмена события
    ↓
К возврату: 2200
    ↓
На сертификат: 2200
Баланс: 800 + 2200 = 3000
```

### 4. Нельзя восстановить исходный сертификат

```
Нужно вернуть N ₽ на сертификат
    ↓
Исходный сертификат
заблокирован / возвращён / аннулирован / не найден?
 ↙             ↘
Нет             Да
 ↓               ↓
Восстановить    Выпустить новый сертификат:
баланс +        • уникальный код
операция        • номинал = N
                • баланс = N
                • статус = активен
                • связь с заказом возврата
                • доставка кода покупателю
                  заказа билетов (email / телефон)
```

В MVP новый сертификат уходит покупателю заказа билетов (тому, кто оформлял возврат / держателю заказа), не «на любую карту» и не произвольному третьему лицу без проверки.

### 5. Частичный возврат нескольких билетов

```
В заказе несколько билетов, один сертификат
    ↓
Возвращаем k билетов из n
    ↓
Считаем стоимость возвращаемых билетов
(+ доля сбора, если сбор возвращаем)
    ↓
Распределяем эту сумму:
сертификат → карта
    ↓
Невозвращаемые билеты и их оплата не трогаем
```

Пропорцию «какой билет чем оплачен» в MVP можно не хранить побилетно, если на заказе есть общий снимок: сколько списано с сертификата и сколько с карты. Тогда возврат k билетов считает денежную базу по правилам события и режет её правилом «сначала сертификат, затем карта» в пределах оставшихся невозвращённых долей каждого источника.

### 6. Сбой одной из веток после успеха другой

```
Сертификат восстановлен, refund по карте упал
    ↓
Не откатываем сертификат автоматически вслепую
    ↓
Статус возврата: «частично выполнен»
    ↓
Повтор refund по карте / ручная выплата
    ↓
После успеха → «выполнен»

Карта вернулась, восстановление сертификата упало
    ↓
Статус: «частично выполнен»
    ↓
Повтор операции / перевыпуск
    ↓
Админ видит обе операции в журнале
```

Атомарность «всё или ничего» между эквайером и балансом сертификата в MVP может быть недоступна. Критерий готовности: расхождение видно, чинится руками, повторный запуск идемпотентен.

### 7. Параллельные запросы

```
Два запроса на возврат одних билетов
    ↓
Блокировка заказа / билетов
    ↓
Первый проходит
    ↓
Второй получает «уже в процессе / уже возвращён»
```

То же для восстановления сертификата: операция баланса только через журнал, с блокировкой строки сертификата.

---

## Что сознательно вне этой схемы (не MVP / другой флоу)

Возврат неиспользованного остатка самого подарочного сертификата через поддержку. Покупка сертификата и его доставка. Применение сертификата на чекауте. Мультисертификаты в одном заказе. Отложенная отправка. Возврат на произвольную карту.

---

## Минимальные статусы, которые схема должна двигать

Заказ / билет: оформлен → возврат в процессе → возвращён (полностью / частично) → ошибка возврата.

Сертификат: полностью использован / частично использован / активен ↔ при восстановлении; при невозможности восстановления исходный не трогаем, живёт новый.

Операции сертификата: восстановление после возврата билета; выпуск (перевыпуск); при ручном разборе — ручная корректировка с инициатором и причиной.
